Architecture

Class hierarchy, design decisions, and runtime data flow

Overview

Image Processor is structured around a classic object-oriented hierarchy. A single abstract base class (Image) defines the shared interface and data storage. Three concrete subclasses provide format-specific loading, normalization, and conversion logic. A separate value type (Pixel) models individual pixels in all three color modes.

The entry point (main.cpp) validates arguments and delegates everything to the static factory method Image::run(), which determines the image format at runtime and creates the appropriate subclass instance.

Image — Abstract Base Class

Files: Image.h / Image.cpp

The Image class is the cornerstone of the design. It owns all pixel data via a 2-D std::vector<std::vector<Pixel>> and exposes the pure-virtual interface that every concrete subclass must implement.

Key non-virtual methods

  • run(arg1, arg2) — static entry point; reads format header, constructs subclass, calls correlation
  • getInputFormat(filename) — opens file, reads magic number, returns format string
  • imageFileIsValid(filename) — validates all header fields and pixel count
  • computeRowChecksums() / computeColChecksums() — build checksum vectors
  • writeRowChecksum() / writeColChecksum() — persist checksums to disk
  • writeImage(filename) — write current image data to a file

Pixel — Value Type

Files: Pixel.h / Pixel.cpp

Pixel is a lightweight value type that can represent a pixel in any of the three color modes.

  • RGB mode: stores three channels — redValue, greenValue, blueValue
  • Grayscale / Binary mode: stores a single intensity — singleValue
  • type: a PixelType enum (RGB, GRAYSCALE, BINARY) tags the active mode
  • Channels that are not in use are stored as -1
  • pixelSum() returns R + G + B — used for binary thresholding

ColorImage — RGB / PPM

Files: ColorImage.h / ColorImage.cpp  ·  Format: P3

Handles the PPM (Portable Pixmap) format. Each pixel stores three channels in the range 0–255. Key behaviours:

  • loadImage() — parses P3 header and reads RGB triplets; tracks min/max per channel
  • regularize() — applies min-max rescaling to all three channels independently: (v - min) × 255 / (max - min)
  • convertToBinary() — thresholds at 382.5 (half of max possible RGB sum of 765)
  • convertToGrayscale() — averages the three channels: (R + G + B) / 3

GrayscaleImage — Grayscale / PGM

Files: GrayscaleImage.h / GrayscaleImage.cpp  ·  Format: P2

The most feature-rich subclass. Handles PGM (Portable Graymap) format and provides the correlation algorithm. Key behaviours:

  • loadImageFast() — reads the entire file into an std::istringstream first, then parses token-by-token, reducing system-call overhead
  • regularize() — same min-max formula as ColorImage but applied to the single channel
  • convertToBinary() — thresholds at 127.5 (half of 255)
  • convertToRGB() — copies intensity into all three channels (grey → RGB)
  • correlation(img1, img2) — computes Pearson coefficient; validates equal dimensions; detects NaN
  • getAverageIntensity(img) — helper used by correlation(); accepts const& to avoid a copy
💡 Performance note The fast-loader reads the file once into a string buffer, then parses it with std::istringstream. This approach was measured with Valgrind Callgrind and reduces total instruction count for a 1920×1080 image by approximately 3%.

BinaryImage — Binary / PBM

Files: BinaryImage.h / BinaryImage.cpp  ·  Format: P1

Handles PBM (Portable Bitmap) format. Each pixel is 0 or 1. Key behaviours:

  • loadImage() — validates P1 header; max-value header field must be 1; stores 0 or 1 per pixel
  • convertToGrayscale() — multiplies by 255: 0 → 0, 1 → 255
  • convertToRGB() — same multiplication applied to all three channels
  • regularize() — no-op; binary images are already in their final range

Design Patterns Used

🏛

Template Method

Image::run() defines the overall algorithm skeleton. Steps like loadImage() and regularize() are deferred to subclasses.

🏭

Factory (Simple)

Image::run() reads the magic number header and instantiates the correct concrete class (ColorImage, GrayscaleImage, or BinaryImage) without the caller knowing which.

🔀

Polymorphism

All image-specific operations are declared virtual in Image and overridden in each subclass, enabling uniform treatment of any image type.

📦

Value Object

Pixel encapsulates pixel state with no identity semantics. Stored by value in the 2-D vector; copy-semantics are used intentionally.
